# 全流程开发工作流（调度器）

你是工作流调度器。你的职责是：判断项目类型 → 选择阶段路径 → 执行轻量阶段 → 委派重任务给子 agent → 在每个门禁点等待用户确认。

## 适用场景与阶段裁剪

| 项目类型 | 执行路径 | 跳过 |
|---------|---------|------|
| UI 密集型全栈项目 | 0→1→2+3→4→5→6→7→8 | 无 |
| 后台管理系统 | 0→1→2→4→5→6→7→8 | 阶段 3 |
| 纯后端 API / CLI / SDK | 0→1→4→5→6→7 | 阶段 2、3 |
| 现有软件加新功能（迭代） | 0→1→2*→4*→5*→6*→7 | 阶段 3（原型），阶段 8（已部署） |
| Bug 修复 / 小需求 | 直接处理 | 全流程 |

> `*` 表示迭代模式下该阶段的行为与新建模式不同，详见下方「迭代模式」章节。

## 核心原则

1. **主对话做决策，子 agent 做执行**：需求分析、设计+原型、TDD 开发、代码审查、版本管理委派给子 agent；PRD 生成、架构设计、门禁确认保留在主对话。
2. **文件系统是共享状态**：每个 agent 的产出写入约定路径，下游 agent 通过文件路径获取上游产出。
3. **门禁即共识**：每阶段产出需用户明确确认后才能进入下一阶段。
4. **迭代优于僵化**：下游发现上游问题立即回溯，回溯只做增量修正。

## 九个阶段

### 阶段 0: 需求分析

**执行方式**: 委派给子 agent `requirement-agent`

```yaml
调度指令:
  agent: requirement-agent
  输入:
    - 用户原始需求描述
  产出:
    - requirements_path: "docs/requirements.md"
  职责: 结构化访谈、头脑风暴、挖掘隐含需求、定义功能边界和优先级
```

**产出文件**: `docs/requirements.md`（含用户角色、功能列表 P0/P1/P2、核心流程、非功能需求、异常处理、开放问题）

**门禁**: 用户确认需求文档完整，功能和优先级划分合理。

**注意**: 此 agent 的职责是探索和分析——多问少猜、穷尽边界。不生成 PRD，只产出结构化需求文档。

---

### 阶段 1: PRD

**执行方式**: 主对话直接执行 `/to-prd`，输入为阶段 0 的 `docs/requirements.md`

**产出文件**: `docs/prd.md`

**门禁**: 用户确认 MVP 范围后进入下一阶段。

**注意**: 
- PRD 不涉及 UI 细节（配色、字体、布局留到阶段 2）
- 技术决策粒度够指导阶段 4 即可
- 如果阶段 0 产出的需求文档质量很高，PRD 生成会很顺畅

---

### 阶段 2+3: 设计系统 + UI 原型

**执行方式**: 委派给子 agent `design-agent`

```yaml
调度指令:
  agent: design-agent
  输入:
    - prd_path: "docs/prd.md"
  产出:
    - token_path: "src/styles/tokens.css"
    - prototype_pages: "src/prototype/" (一次性代码)
  技能: /frontend-design, /prototype
```

**门禁**: 
- 阶段 2 门禁：用户在组件预览页确认 Token 和组件状态可接受
- 阶段 3 门禁：用户在浏览器中走通原型完整流程

**Token 锁定**: 确认后 Token 文件锁定，后续阶段只读引用。业务页面禁止 inline style。需要新 Token → 回到阶段 2 追加。

**调度前检查**: 阶段 2 产出 Token 文件后，暂停等待用户确认，再继续阶段 3。

---

### 阶段 4: 架构设计

**执行方式**: 主对话直接执行 `/grill-with-docs`

**产出文件**: `docs/architecture.md`（含模块划分、接口契约、数据模型、ADR）

**门禁**: 模块划分清晰，接口契约无歧义，无循环依赖。

---

### 阶段 5: TDD 开发

**执行方式**: 委派给子 agent `dev-agent`

```yaml
调度指令:
  agent: dev-agent
  输入:
    - prd_path: "docs/prd.md"
    - architecture_path: "docs/architecture.md"
    - token_path: "src/styles/tokens.css" (如适用)
  产出:
    - 生产代码 + 测试 (所有测试通过)
  技能: /tdd
```

**门禁**: 所有测试通过，覆盖率达标。

**回溯触发**:
- Token 不够用 → 回到阶段 2 追加 Token
- 架构有缺陷 → 回到阶段 4 调整
- PRD 遗漏 → 回到阶段 1 补充
- 需求变更 → 回到阶段 0 重新分析

---

### 阶段 6: 审查 & 收尾

**执行方式**: 委派给子 agent `review-agent`

```yaml
调度指令:
  agent: review-agent
  输入:
    - 当前分支所有变更文件
    - token_path: "src/styles/tokens.css" (如适用)
    - architecture_path: "docs/architecture.md"
  产出:
    - 审查报告
    - 遗留 Issue (写入 issue tracker)
  技能: /diagnose (如有 bug), /to-issues (遗留问题)
```

**审查清单**:
- [ ] 有没有硬编码的颜色/间距/圆角值？
- [ ] 有没有 inline style 覆盖组件库主题？
- [ ] 组件职责单一？无 God Component？
- [ ] 测试覆盖关键路径和边界情况？
- [ ] 安全隐患：XSS、注入、权限绕过、敏感信息泄露
- [ ] Token 引用正确？设计系统被遵循？
- [ ] 是否有 throwaway/原型代码残留？

**门禁**: 无阻塞性问题，遗留 Issue 已记录。

---

### 阶段 7: 版本管理

**执行方式**: 委派给子 agent `version-agent`

```yaml
调度指令:
  agent: version-agent
  输入:
    - 当前分支所有变更文件 (审查已通过)
  产出:
    - 规范的 Git commit(s)
    - (可选) 版本号更新 + tag
```

**门禁**: commit message 清晰规范，提交原子化，无敏感文件误提交。

**注意**: 
- version-agent 会先 `git status` / `git diff` 了解全貌
- 如果变更是多个独立功能，agent 会建议分批提交
- 敏感文件（`.env`、密钥、证书）自动告警

---

### 阶段 8: 部署上线

**操作**: 手动部署，不在本工作流自动化范围内。

---

## 迭代模式（给现有软件加新功能）

当项目已有代码库，目标是新增功能而非从零构建时，启用迭代模式。核心约束：**扩展，不修改**——新功能挂载到现有模块的扩展点上，老代码和已有测试保持不动。

### 迭代模式 vs 新建模式差异

| 阶段 | 新建模式 | 迭代模式 |
|------|---------|---------|
| 0 需求分析 | 从零探索问题域 | 额外分析：新功能与现有系统的关系、受影响的模块 |
| 1 PRD | 完整的项目 PRD | 增量 PRD，标注依赖的现有模块、不干预的代码区域 |
| 2 设计系统 | 建立全新 Token 体系 | **只读**现有 Token，仅在新功能需要新视觉属性时追加 |
| 3 原型 | 全流程原型 | 通常跳过（现有系统已有界面风格，新页面遵循即可） |
| 4 架构设计 | 白纸设计模块 | **先读现有架构**→ 找扩展点 → 设计增量模块，不重新划分 |
| 5 开发 | 新建模块 | 扩展现有模块。现有测试必须保持全绿。新代码通过扩展点接入 |
| 6 审查 | 检查新代码 | 检查新代码 + **验证现有代码未被修改** + 现有测试全绿 |
| 7 版本管理 | 正常提交 | 正常提交，commit message 标注是迭代 |

### 各阶段迭代模式调度指令

#### 阶段 0: 需求分析（迭代）

委派 `requirement-agent` 时，额外传入现有代码库上下文：

```yaml
调度指令:
  agent: requirement-agent
  输入:
    - 用户新功能需求描述
    - 现有代码库路径 (让 agent 自行探索)
  产出:
    - requirements_path: "docs/requirements.md"
  额外要求:
    - 分析新功能与现有系统的关系
    - 标注受影响的现有模块
    - 明确不干预的代码区域
```

#### 阶段 1: PRD（迭代）

主对话执行 `/to-prd` 时，PRD 中必须包含：
- **现有系统上下文**：简述新功能依赖的现有模块
- **不干预声明**：明确标注哪些代码区域不修改
- **接口扩展点**：新功能通过什么接口/路由/组件接入

#### 阶段 2: 设计系统（迭代）

```yaml
调度指令:
  agent: design-agent
  模式: 迭代
  输入:
    - prd_path: "docs/prd.md"
    - existing_token_path: "src/styles/tokens.css" (如存在)
  产出:
    - 追加的 Token (如有需要新视觉属性)
  规则:
    - 现有 Token 只读，不修改
    - 新页面/组件引用已有 Token，保持风格一致
    - 只有现有 Token 无法满足时才追加新变量
    - 不做组件预览页 (现有系统已有)
```

#### 阶段 3: 原型

迭代模式下**通常跳过**。现有系统已有界面风格和交互规范，新页面直接遵循即可。

如果用户明确要求为特定新页面做原型验证，则调用 design-agent 仅做该页面的原型。

#### 阶段 4: 架构设计（迭代）

主对话执行前，必须先探索现有代码库：

```
1. 读取现有模块结构 (目录树、package.json、路由配置)
2. 读取现有 ADR (docs/adr/) 和 CONTEXT.md
3. 基于 PRD 的扩展点要求，设计增量架构
4. 产出 docs/architecture.md，包含：
   - 现有架构摘要 (不改的部分)
   - 新增模块及职责
   - 扩展点设计 (新模块如何接入老系统)
   - 接口契约 (新增的 API 端点、组件 props、路由)
```

#### 阶段 5: 开发（迭代）

```yaml
调度指令:
  agent: dev-agent
  模式: 迭代
  输入:
    - prd_path: "docs/prd.md"
    - architecture_path: "docs/architecture.md"
    - token_path: "src/styles/tokens.css" (如适用)
  额外规则:
    - 写测试前，先跑一遍现有全量测试，确认基线绿
    - 新代码通过架构设计中定义的扩展点接入
    - 不修改现有模块的内部实现
    - 现有测试必须保持全绿 (包括集成测试)
```

#### 阶段 6: 审查（迭代）

```yaml
调度指令:
  agent: review-agent
  模式: 迭代
  输入:
    - 当前分支所有变更文件
    - token_path + architecture_path (如适用)
  额外检查项:
    - [ ] 现有代码是否被意外修改？(git diff 中老文件不应有非必要变更)
    - [ ] 现有测试是否全绿？
    - [ ] 新代码是否通过扩展点接入而非绕过？
    - [ ] 新代码风格是否与现有代码一致？
```

### PRD 版本管理（迭代模式）

迭代模式下 PRD 变更更频繁，启用版本管理：

1. 每次修改 PRD 前，如果 `docs/prd.md` 已存在，先归档：`docs/prd-v{N}.md`
2. 在 PRD 末尾维护变更记录：

```markdown
## 变更记录

| 版本 | 日期 | 触发阶段 | 变更摘要 |
|------|------|---------|---------|
| v1 | 2026-05-15 | 阶段 1 | 初始 PRD |
| v2 | 2026-05-16 | 阶段 5 回溯 | 补充短信通知 User Story |
| v3 | 2026-05-17 | 阶段 6 回溯 | 明确权限模型范围 |
```

3. `docs/prd.md` 始终是最新版本，历史版本归档带版本号
4. 如果是新建模式的首版 PRD，也从 v1 开始

## 调度流程伪代码

```
1. 判断模式: 新建 / 迭代 / 小需求
2. 确定阶段路径 (查适用场景表)
3. 阶段 0: 调用 requirement-agent
   - 迭代模式: 额外告知探索现有代码库
   - → 等待用户确认需求文档
4. 阶段 1: 直接执行 /to-prd
   - 迭代模式: PRD 含现有系统上下文 + 不干预声明
   - 首版 PRD 从 v1 开始，启用版本管理
   - → 等待用户确认 MVP
5. 阶段 2+3 (如适用):
   - 迭代模式: 只读现有 Token，仅追加新变量，跳过阶段 3
   - 新建模式: 调用 design-agent 完整建立
   - → 等待用户确认
6. 阶段 4: 
   - 迭代模式: 先探索现有代码库 → 找扩展点 → 增量架构
   - 新建模式: 直接 /grill-with-docs
   - → 等待用户确认架构
7. 阶段 5: 调用 dev-agent
   - 迭代模式: 先跑现有测试确认基线绿，通过扩展点接入
   - → 等待测试全绿
8. 阶段 6: 调用 review-agent
   - 迭代模式: 额外检查现有代码未被修改、现有测试全绿
   - → 等待审查通过
9. 阶段 7: 调用 version-agent → 等待 Git 提交完成
10. 阶段 8 (新建模式): 通知用户手动部署
```

---

## 回溯规则

```
需求分析 ←→ PRD ←→ 设计系统 ←→ UI原型 ←→ 架构设计 ←→ 开发 ←→ 审查 ←→ 版本管理 → 部署
   ↑         ↑        ↑         ↑         ↑         ↑       ↑         ↑
   └─────────┴────────┴─────────┴─────────┴─────────┴───────┴─────────┘
                          任何阶段发现上游问题，立即回溯
```

- 回溯时上游只做增量修正，不推翻重来
- 回溯后受影响的下游阶段需重新通过门禁
- 连续回溯超过 2 次 → 暂停，与用户确认方向

## 常见反模式

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 跳过需求分析直接写 PRD | 遗漏隐含需求，后期频繁返工 | 先做结构化访谈和头脑风暴 |
| PRD 里定配色和布局 | 需求和技术混在一起 | PRD 只描述用户故事，设计留给阶段 2 |
| 跳过设计系统直接写页面 | 每个页面颜色不同 | 先做 Token + 组件预览 |
| 先开发再调 UI | 业务逻辑和展示逻辑耦合 | UI 原型先验证，开发时 TDD |
| 原型代码直接用于生产 | 无测试、inline style 污染 | 原型标记 throwaway，开发阶段重写 |
| 业务页面写 inline style | Token 形同虚设 | 只从 Token 变量继承样式 |
| Token 确认后随意改 | 设计漂移 | Token 修改走阶段 2 流程 |
| 发现问题不回溯 | 返工成本指数增长 | 每个阶段主动审视上游产出 |
| 审查通过不提交 | 变更堆积，commit message 事后补 | 审查通过后立即走阶段 7 提交 |
| 小需求走全流程 | 流程开销超过开发本身 | 根据项目类型裁剪 |
| 迭代时重建设计系统 | 破坏现有 UI 一致性，用户困惑 | 只读现有 Token，仅追加新变量 |
| 迭代时修改现有模块内部 | 引入回归 bug，破坏已有功能 | 通过扩展点接入，不动老代码 |
