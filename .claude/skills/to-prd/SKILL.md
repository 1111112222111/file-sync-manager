此 skill 基于当前对话上下文和对代码库的理解生成 PRD。不要采访用户 —— 直接综合你已知的信息即可。

Issue 跟踪器和 triage 标签词汇应已提供给你 —— 如未提供，请运行 `/setup-matt-pocock-skills`。

## PRD 更新规范

当在已有 PRD 基础上迭代新增内容时，必须遵循以下标注规范，确保读者能清楚区分原有内容与新增内容：

### 新增内容标注

- 使用 **🆕 标记** + 修改日期，格式：`🆕 功能名称 \`YYYY-MM-DD\``
- 在表格中新增"备注"列，标注"原有"或新增日期
- 新增的独立模块作为独立的 `🆕` 章节呈现

### 被替换内容标注

- 使用 **删除线** `~~旧内容~~` → `新内容` 保留变更痕迹
- 在表格"备注"列说明变更时间

### 架构图更新

- 在架构图中用 `🆕 组件名 ← YYYY-MM-DD` 注释标记新增组件
- 不要删除原有组件，新增组件叠加在原图上

### 时间戳格式

- 统一使用 `YYYY-MM-DD` 格式
- 每次迭代的新增内容使用当次修改日期

### 发布前强制更新

- **每次打包或发布前**，必须将本次所有变更内容同步更新到 PRD 文档中
- 包括但不限于：新增功能、数据模型变更、分类规则调整、UI 交互修改、移除的旧实现
- 更新后需将 PRD 随代码一同提交到 Git 仓库
- 确保 PRD 文档始终反映最新的产品功能状态

### 示例

```markdown
## 交互模式

| 功能 | 说明 |
|------|------|
| 系统托盘 | 原有功能描述 |
| 🆕 快捷键自定义 | `2026-05-18` 可在设置中录制自定义组合键 |

## 数据模型

```typescript
interface Memo {
  type: 'link' | 'todo' | 'text' | 'clipboard'; // 🆕 新增 clipboard 类型
}
```

## 窗口规格

| 项目 | 值 | 备注 |
|------|-----|------|
| ~~透明窗口~~ | ~~`transparent: true`~~ | `2026-05-18` 改为实色背景 |
| 🆕 窗口背景 | `#1a1a2e` / `#f5f5f8` | `2026-05-18`，随主题切换 |
```

## 流程

1. 如果尚未了解，先探索仓库以理解代码库当前状态。在整个 PRD 中使用项目的领域词汇表，并尊重所涉及领域的任何 ADR（架构决策记录）。

2. 勾勒出完成实现所需构建或修改的主要模块。积极寻找提取深层模块的机会，这些模块应能独立测试。

深层模块（与浅层模块相对）是指将大量功能封装在一个简单、可测试、极少变化的接口中的模块。

与用户确认这些模块是否符合预期。与用户确认希望为哪些模块编写测试。

3. 使用下方模板编写 PRD，然后将其发布到项目 Issue 跟踪器。打上 `ready-for-agent` triage 标签 —— 无需额外的 triage 流程。

<prd-template>

## 问题陈述

从用户的角度描述用户面临的问题。

## 解决方案

从用户的角度描述问题的解决方案。

## 用户故事

一个详尽的、编号的用户故事列表。每条用户故事遵循以下格式：

1. 作为一个<角色>，我想要<功能>，以便<收益>

<user-story-example>
1. 作为一个手机银行客户，我想要看到账户余额，以便我能更好地做出消费决策
</user-story-example>

用户故事列表应极其详尽，覆盖该功能的所有方面。

## 实现决策

已做出的实现决策列表，可包括：

- 将构建/修改的模块
- 这些模块中将被修改的接口
- 开发者的技术澄清说明
- 架构决策
- Schema 变更
- API 契约
- 具体的交互细节

不要包含具体文件路径或代码片段。它们可能很快过时。

例外：如果原型产出了一个能比文字更精确地编码某项决策的代码片段（如状态机、reducer、schema、类型定义），将其内联到相关决策中，并简要注明它来自原型。裁剪到决策关键部分 —— 不是完整可运行的 demo，只保留重要部分。

## 测试决策

已做出的测试决策列表，包括：

- 什么是好的测试的描述（只测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的参考先例（即代码库中类似类型的测试）

## 不在范围内

描述此 PRD 范围之外的内容。

## 补充说明

关于此功能的任何额外说明。

</prd-template>
